# 0008. Dual Distribution: Standalone `dotnet new` Template Package

## Status

Accepted

## Context

`templates/webapi` was always spec-compliant with the .NET Template Engine
(`.template.config/template.json`, identity `Dorn.Templates.WebApi`, short name
`dorn-webapi`) and, per ADR 0007, fully self-contained. That self-containment was
explicitly justified in ADR 0007 as keeping the door open for future NuGet template
packaging.

Despite that groundwork, the original implementation plan deferred actually building the
packaging step, so `eng/scripts/pack-templates.ps1` shipped as a stub (`exit 1` plus a
TODO), and the `dorn` CLI's embedded `Microsoft.TemplateEngine.Edge` host (ADR 0002) was
the only supported way to generate a project.

The user later clarified that a standalone, vanilla-`dotnet new`-installable template
package is a core v1 goal, not a nice-to-have: `dotnet new install Dorn.Templates.WebApi`
must work without ever installing the `dorn` CLI, and the same
`<PackageType>Template</PackageType>` mechanism that enables it is what Visual Studio's
"Create a new project" search uses to discover third-party templates. This ADR reverses
that one deferral; ADR 0002's embedded Template Engine and ADR 0007's shared-file-sync
are prerequisites it builds on, not decisions it revisits.

## Decision

`templates/webapi` is now distributed through two independent channels pointing at the
same template content:

1. **`dorn new webapi`** (ADR 0002), using the isolated Template Engine host under
   `~/.dorn/template-engine`, unchanged by this ADR.
2. **`dotnet new install Dorn.Templates.WebApi`** (new), a standard NuGet package with
   `<PackageType>Template</PackageType>`, usable with vanilla `dotnet new`, discoverable
   in Visual Studio's "Create a new project" search.

The packaging project lives at
`eng/packaging/Dorn.Templates.WebApi/Dorn.Templates.WebApi.csproj`, outside
`templates/webapi/`: NuGet's content-packing glob
(`Content Include="../../../templates/webapi/**/*"`) only reads files for packaging, so
the `.csproj` never becomes part of `templates/webapi`'s own tree (matching the `eng/`
convention for tooling that must not ship to end users). Placing it inside
`templates/webapi/` was rejected: the Template Engine copies everything under the
template root except what `template.json` excludes, so the packaging project would get
instantiated into every generated solution.

`eng/scripts/pack-templates.ps1` is now a real script (was a stub) that runs `dotnet pack`
against the packaging project, versioned via an optional `-Version` parameter (default
`0.1.0-dev`), emitting to `./artifacts`. (Its original shared-file drift pre-check was
later retired by ADR 0010.)

`.github/workflows/ci.yml` runs this script and a full install → list → generate → build
→ uninstall smoke cycle on `ubuntu-latest`.

Publishing to NuGet.org is **not** part of this change, same deferred status as the
`dorn` CLI's own publishing (see the `TODO(eng)` marker in `.github/workflows/ci.yml`).
Until then, `dotnet new install Dorn.Templates.WebApi` is documented as installing from a
local `./artifacts/*.nupkg` path.

## Consequences

- **Two distribution channels now need to be kept working, but there is no drift risk
  between them.** Both are thin plumbing over the same `templates/webapi/` content; the
  NuGet package is generated by packing it as-is. The only artifact that could drift is
  the packaging `.csproj`'s include/exclude glob, a small, reviewable surface.
- **`templates/webapi` must remain self-contained for both channels to keep working**;
  ADR 0007 established this, ADR 0010 later changed how cross-template code is shared
  without changing the requirement.
- CI now smoke-tests both paths: `dorn new webapi` (via `templates/tests`) and
  `dotnet new install`/`dotnet new dorn-webapi`/`dotnet new uninstall` (new ubuntu-only
  step).
- Visual Studio discoverability comes free from `<PackageType>Template</PackageType>`,
  gated on the same not-yet-implemented NuGet.org publish step.
- **Local verification (this change)**: `pwsh eng/scripts/pack-templates.ps1` produced
  `./artifacts/Dorn.Templates.WebApi.0.1.0-dev.nupkg`; install, generate, build, and the
  EF Core auto-migrate-on-startup path (via a real `POST /api/todos`) all succeeded, and
  uninstall cleanly removed `dorn-webapi`. The `dorn` CLI's own isolated-host path kept
  working throughout, confirming the two caches are genuinely independent.
